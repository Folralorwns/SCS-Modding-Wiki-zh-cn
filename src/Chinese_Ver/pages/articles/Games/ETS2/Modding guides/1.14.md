# Games/ETS2/Modding guides/1.14

## 建议

- 一些使用 "sc" 后缀或前缀的新模型仍在制作中，很可能在后续某个补丁中发生较大变化。因此，建议你目前避免在自己的模组中使用它们。
- 在基于原始模型制作你的模型时，请同时将它所使用的**全部**原始 /automat/ 文件加入你的模组。这些文件的名称是根据其内容生成的 SHA1 哈希值，因此每当我们以任何方式更改材质参数时，都会使用另一个文件来存储它们，而如果没有其他模型使用原始参数，原始文件可能会不复存在。
- 修改原始模型时，务必包含该模型的**所有**组件（pmg+pmd），而不只是你更改过的那些。否则一旦我们更改该模型，你就有可能遇到崩溃。
- 一如既往，向支持多文件方式的文件（例如 road_look.sii）添加新对象时，**强烈建议**在名称中使用后缀或前缀，以避免与我们在补丁中新增的对象冲突。否则当新补丁出现时，你可能需要使用批量重命名功能（参见批量重命名）来修复冲突。

## 如何转换地图

- 如果你正在覆盖 **game_data.sii**，请更新车库和卡车经销商的定义（游戏数据）
- 为没有质量属性的标志牌定义 mass 属性（将会在日志中看到）
- 使用替换对话框（F3，"Prefab node correction"）把我们在某些预制件中新增的节点添加到地图中
- 检查我们已修正过节点的预制件的周边区域（见 #Corrected prefab nodes）
- 为所有没有 City item 区域的城市创建交通区域项（见 #City items vs. 'city speed limits'）
- 保存地图
- 执行重建（F8）
- 保存地图

### 游戏数据

**game_data.sii** 中的 **tiny_garage/small_garage/large_garage** 和 **truck_dealer_exterior/truck_dealer_interior** 属性已改为带 's' 后缀的数组。如果你的模组覆盖了此文件，则必须按照该文件的官方版本更新这些属性。

### 仪表板模板

**dashboard_text.sii** 现在在档案选择之后加载（因此可以通过常规的模组选择机制进行修改），并支持多文件。为新卡车添加仪表板时，请使用多文件机制。

### 路线顾问

我们更改了顾问 UI 处理欧洲大陆版和英国版变体的方式。如果你覆盖了它，需要确保修改后的 UI 包含所有必需的组件。

### 货物

货物的定义已拆分为公共数据以及用于运输该货物的各个挂车的定义。

- 公共参数和以前一样存储在 **/def/cargo/&lt;name&gt;.sii&lt;/name&gt;** 中的单元 **cargo.&lt;name&gt;&lt;/name&gt;** 里。
- 用于运输该货物的挂车现在以一组文件的形式存储在 **/def/cargo/<name/**.sii* 中。文件名没有技术上的限制，但强烈建议以挂车单元的名称作为其基础。

### 气候

天气系统现在可以区分 "climates"。可以有多种气候，每种气候都有自己的一套好天气和恶劣天气。可用气候的列表位于文件 **climate.sii** 中，并支持多文件。添加新气候时，请使用多文件机制。

定义气候的文件示例：

```
SiiNunit
{
climate_profile : climate.subtropical {
 bad_weather_factor: 0.07
}
}
```

每种气候的天气配置位于文件夹 **climate/<name_of_climate>/bad.sii** 和 **climate/<name_of_climate>/nice.sii** 中。这些天气配置的格式与之前相同，只是默认配置从 **nice_weather.sii** 和 **bad_weather.sii** 移到了 **climate/default/nice.sii** 和 **climate/default/bad.sii**。如果你的模组覆盖了这些文件，则必须更新为新的文件。注意天气配置中单元名称的唯一性。

每个地图扇区都分配了一种气候，这意味着你地图的不同部分可以有不同的气候。新扇区会自动分配默认气候。你可以通过创建文件 **map/<name_of_map>.climate.sii** 并在编辑器中保存地图来覆盖这一设置。保存时，气候的名称会存储在各地图扇区文件内部。

此类文件的示例：

```
SiiNunit
{
map_sector_climate : map.europe.climate
{
 coordinate[]: (-2, 8)
 climate[]: subtropical
 coordinate[]: (-3, 8)
 climate[]: subtropical
}
}
```

### 交通的变更

#### 新的 AI 卡车模型

为节省性能，所有 AI 卡车模型都已优化。现在每辆卡车的底盘和所有附加组件都**合并到单个模型**中。卡车存储定义文件（*/base/def/vehicle/truck_traffic_storage.sii*）现在包含新的定义路径。旧系统（手动组装车辆）仍然受支持。如果你的模组包含修改过的 AI 卡车车辆定义，请检查 *truck_traffic_storage.sii.* 中是否有正确的定义。

#### 交通区域

- 它们通过在编辑器中创建 **traffic area items** 来定义。
- 创建交通区域主要是为了能够指定**区域交通规则**。
- 交通区域的形状可以是任意 N 边形
- **任何**交通规则（来自 *traffic_rules.sii*）都可以用作交通区域规则（尽管有些规则作为“区域”规则并不合理，例如 'give way'、'stop line' 等）

##### 常用区域交通规则

- **禁止卡车区域**
  - 阻止卡车（带或不带挂车）进入该区域或在区域内生成
- **城市区域**
  - **规则区域应与 'city start' 和 'city end' 交通标志相对应**
  - 标记要使用 '**city speed limits**' 的区域（编辑器中的 'CITY ITEMS' 不再用于此目的！）

#### City items 与 'city speed limits'

到目前为止，City item 用于定义“城市内部”的区域，即应使用“城市规则”（如城市限速）的区域。然而，City item 可使用的形状非常有限。这常常导致限速检测方面的错误（城市之外的区域表现得像是在城市内部，反之亦然）。

从本补丁开始，**现在使用交通区域项而非 City item 来定义城市限速**。如果你的地图模组包含一些新城市，请**在新城市上创建相应的交通区域项，并将 '*Traffic rule*' 属性设置为 '*City area*'**。否则，这些区域将不会表现得像城市区域。

### 导航的变更

预制件上的导航（GPS）已得到改进。现在它会**直接从预制件导航曲线中提取 'navigation information'**，以确定节点之间哪些路径是有效的。这使得能够生成合理得多的导航路线，尤其是在穿越“单向”预制件和道路时。不过，这也假定所有预制件都已用导航曲线正确连接其节点。如果你有修改过的地图并遇到与导航相关的错误，请**检查起点和终点导航点之间的预制件中是否缺少导航曲线**。
